- 核实日期：2026-03-14
- 适用范围：当前仓库主线代码、现有主线文档与当日本地验证结果
- 事实来源：`README.md`、`main.py`、`core/`、`logic/`、`vision/`、`input/`、`ui/`、`tests/`

## 1. 项目定位

AradVision 当前不是“通用 YOLO 全自动平台”，而是一个围绕 DNF 固定路线自动化研究的 Python 项目。当前仓库主线已经收敛到《歼灭追击战》固定路线 MVP，重点解决以下问题：

1. 稳定获取游戏画面，优先支持 Windows 下的 `WGC`，失败时按配置降级到 `MSS`。
2. 用轻量 Reader 而不是通用 YOLO 作为当前主决策输入，包括主画面状态、小地图推进状态、HP/MP 与若干 UI 信号。
3. 用固定路线控制器替代旧的“通用怪物/拾取/导航”主线，先跑通单副本、单路线、单职业画像的闭环。
4. 保留 UI、旧状态机、旧世界模型和检测器抽象作为兼容层或观察面，而不是当前默认决策主线。

在长期方向上，项目目标已经明确为一条分层演进路线：

1. 短期先把《歼灭追击战》固定路线 MVP 做实、做稳。
2. 中期补齐多副本配置切换与双链路能力，让已适配副本继续走固定路线，未适配副本逐步接入通用 YOLO 流程。
3. 长期在结构化感知和高层动作边界之上接入 LLM 决策层，但不让 LLM 直接承担底层控制。

当前控制台与 UI 线程的实际主循环都已经接到 `FixedRoutePipeline`，主线数据流是：

```text
CaptureEngine
  -> MainViewReader / StateReader / MinimapReader
  -> GuardLayer
  -> RouteRunController / MaintenanceController
  -> InputDriver
```

### 2.2 保留但不是当前默认主线的模块

以下模块仍然存在，并且有测试或 UI 观察面价值，但不是当前《歼灭追击战》固定路线 MVP 的默认决策链路：

| 模块 | 当前角色 |
| --- | --- |
| `logic/world_model.py` | 旧世界模型，保留兼容与观察用途 |
| `logic/bot_fsm.py` | 旧状态机，仍有单测与集成测试，但控制台主循环不再使用它做最终决策 |

| `vision/coordinate_mapper.py` / `logic/combat.py` / `logic/path_planner.py` | 旧通用战斗/对齐/导航能力，仍保留但不是当前主叙事中心 |
| `ui/timeline_window.py` | 辅助工作台，不是默认运行入口 |

### 2.3 当前实现边界

基于代码和配置，当前主线已经明确“做什么”和“不做什么”：

当前版本包含：

1. 单副本固定路线推进。
2. 轻量视觉状态识别。
3. 守护层药水逻辑与中止逻辑。
4. 副本结束后的维护流程状态切换。
5. 可选控制台运行和可选 PyQt 控制面板。

当前版本不包含：

1. 通用 YOLO 决策主链路。
2. 通用导航与通用拾取主线。
3. 切角色、副本选择、复杂副本外 UI 自动化。
4. 真实卖店点击与完整维护动作闭环。
5. 多副本、多路线、多职业策略编排。
6. `LLM Policy` 或任何形式的高层智能决策接入。

### 2.4 当前找门策略口径

当前已实现事实：

1. `RouteRunController` 当前根据 `room_scripts.expected_exit_direction`、`exit_action_template` 与 `MinimapPathState` 触发房间推进，不做整屏通用找门或完整通用寻路。
2. `MinimapReader` 当前负责推进状态校验与异常信号提示，不承担像素级导航职责。
3. `door_confirmation_roi` 已在配置结构中预留，但当前还没有形成完整的“门前确认 -> 对准 -> 进门”闭环。

后续实现建议：

1. 继续保持“固定路线决定方向、视觉做局部辅助”的主线，不把路线选择交给 YOLO。
2. 后续可把房间推进细化为“去目标边缘工作区 -> 局部扫描门 -> 对准并进门”三阶段。
3. 人物位置建议主用 YOLO `hero`；多门筛选只在目标方向局部窗口内进行。
4. 脚本失败后优先做房间级纠偏和局部恢复，恢复主线先绕行和回退，跳跃只作为最后兜底，再视情况补更通用的恢复逻辑。

## 3. 目标架构与阶段路线

### 3.1 四层目标架构

在不改变当前 MVP 交付目标的前提下，项目长期应演进到四层结构：

1. 平台层：采集、输入、窗口、坐标、熔断等与运行环境直接相关的能力。
2. 游戏适配层：当前游戏的场景识别、UI 识别、YOLO 检测、对象类型和动作语义。
3. 玩法策略层：具体玩法如何运行，例如固定路线副本和未来通用 YOLO 副本流程。
4. 决策层：规则策略与未来 LLM 策略，负责高层任务选择、链路切换和异常恢复。

这个四层结构是长期目标，不代表当前代码已经全部实现。当前仓库主要已落在 DNF 的平台层首版、游戏适配层首版和固定路线玩法策略层。

### 3.2 双链路原则

后续演进应遵守以下原则：

1. 已适配副本走 `ROI + 固定流程`。
2. 未适配副本走 `YOLO + 通用流程`。
3. 静态 UI 元素优先使用固定 ROI / 规则法。
4. 动态空间目标优先使用 YOLO。
5. `LLM` 只做高层决策，不直接发底层键鼠。

### 3.3 分阶段目标

项目后续不再只用“三阶段能力堆叠”来描述，而是采用“分层目标 + 分阶段推进”的口径：

1. 当前阶段：固定路线 MVP。
2. 下一阶段：多副本配置管理与双链路骨架。
3. 后续阶段：通用 YOLO 流程。
4. 终局阶段：LLM 高层决策层。

## 4. MVP 定义

### 4.1 当前 MVP 是什么

当前项目的 MVP 不是“把整套 DNF 自动化全部做完”，而是：

在受控环境下，针对《歼灭追击战》这一条固定路线，完成一条可验证、可回归、可逐步切换到真实环境的自动化主链路。

换句话说，当前 MVP 的核心目标是先证明下面这件事能稳定成立：

1. 捕获链路能拿到目标窗口画面。
2. Reader 能识别出战斗、清房、转场、BOSS、通关等关键状态。
3. 固定路线控制器能依据这些状态发出合理动作。
4. 守护层能在低血、低蓝、药水不足等情况下优先兜底。
5. 跑完一轮后能进入维护流程的安全 `dry run`。
6. 整套链路可以在 Mock 环境里回归测试，再逐步切到真实捕获和真实输入。

### 4.2 当前 MVP 的最小验收口径

若按当前代码边界定义 MVP，最小验收应至少包括：

1. `main.py` 控制台模式可跑通固定路线主链路。
2. `main.py --ui` 在安装 PyQt5 的环境中可启动控制面板，并由引擎线程驱动主链路。
3. `dungeon_run` 的 ROI、阈值和房间脚本可支撑《歼灭追击战》至少一条真实路线。
4. 捕获后端在 Windows 环境下可验证 `WGC` 与 `MSS` 的选择和降级行为。
5. 维护流程保持 `dry run`，不把高风险动作直接放进 MVP 首版。

## 6. 当前主要缺口与风险

### 6.1 主线能力缺口

1. `configs/config.yaml` 中 `dungeon_run.room_scripts` 当前只有 2 个示例房间，真实《歼灭追击战》路线仍需逐房间补齐。
2. `StateReader` 里的 `free_slots` 目前固定返回 `999`，说明背包空格读取还是占位实现。
3. `MaintenanceController` 目前只做状态切换和日志语义，真实卖店、修理、补给并未落地。
4. `MinimapReader.read()` 虽然保留了 `expected_room_index` 和 `is_last_normal_room` 参数，但当前实现里并未真正使用。
5. `detector.type` 除 `mock` 外当前仍会回退到 `MockYoloDetector`，真实 YOLO 检测器还没有成为现行主链路能力。
6. 房间推进当前仍以“固定模板 + 过图超时重试”为主，固定路线下的三阶段找门与分层纠偏尚未落地。

### 6.2 配置与架构收口缺口

1. `dungeon_run.enabled` 已能被配置解析，但当前代码中没有实际开关逻辑，配置项尚未真正生效。
2. `main.py`、`EngineThread` 仍保留 `WorldModel` 和 `BotFSM` 的初始化与兼容叙事，说明架构切换已完成主循环收口，但兼容层还没有完全清理。
3. UI 中仍有若干 `TODO`，例如主题切换、参数面板持久化、部分状态同步，这意味着 UI 更适合做观察和控制入口，而不是当前版本的完备运维面板。

### 6.3 验证与工程质量风险

1. `tests/` 目录当前仍有 3 个失败用例，影响“核心目录全绿”的基线。
2. `pytest -q` 会把 `scripts/test_*.py` 也收进来，当前没有 `PyQt5` 就会在收集阶段失败，说明测试分层和依赖分层还不够清晰。
3. `scripts/label_guide.py` 的语法错误会影响全量 `compileall`，不利于仓库级静态检查。
4. WGC 的真实效果仍需在真实 Windows 机器上继续验证，尤其是遮挡、独占全屏和依赖版本差异场景。

## 7. 建议的下一阶段开发计划

### 阶段 P0：把当前 MVP 做成“可实机复验”

这一阶段不追求功能扩张，先把《歼灭追击战》固定路线做扎实：

1. 完成真实路线的 `room_scripts`、ROI 和阈值复核。
2. 让 `dungeon_run.enabled` 真正控制主链路启停或模式切换。
3. 把 `StateReader` 中背包空格、重量、药水状态的占位字段替换为真实读取。
4. 在 Windows 真实环境完成 `WGC -> MSS` 的后端验证和 `F12` 熔断验证。
5. 在不改写当前主线的前提下，把固定路线下的找门、局部扫门与分层纠偏规则落实为可实机复验的实现。

### 阶段 P1：把仓库质量基线收口

这一阶段解决“主线能跑，但仓库整体还不干净”的问题：

1. 修复 `coordinate_mapper` 的 2 个失败测试。
2. 修复 `input_driver` 的非法按键异常语义，使测试与实现一致。
3. 处理 `scripts/label_guide.py` 的语法错误。
4. 给 UI 脚本测试加依赖隔离、标记或单独入口，避免 `pytest -q` 在无 PyQt5 环境直接收集失败。

### 阶段 P2：补齐双链路骨架，但不改变当前 MVP 主线

这一阶段开始补长期架构需要的最小接口，但默认运行链路仍是固定路线：

1. 引入多副本配置切换所需的 `DungeonRegistry / DungeonProfile` 一类注册骨架。
2. 引入 `GamePipeline` 抽象，让 `FixedRoutePipeline` 成为统一玩法接口的一个实现。
3. 引入 `GlobalSceneReader / PerceptionSnapshot / PerceptionAssembler` 这类感知汇总边界。
4. 保持现有 Reader、ROI 和固定路线资产可继续复用，不做推倒式重写。

### 阶段 P3：引入通用 YOLO 流程

这一阶段才开始建设未适配副本所需的通用流程：

1. 新增 `GeneralYoloPipeline` 或等价的通用玩法链路。
2. 让静态 UI 继续由规则法读取，动态空间目标逐步交给 YOLO 检测。
3. 在不回退当前 MVP 的前提下，尝试把未适配副本纳入通用链路。
4. 继续保留固定路线链路，避免已适配副本被通用方案反向拖慢。

### 阶段 P4：接入 LLM 高层决策层

这一阶段才考虑引入智能化策略能力：

1. 在结构化感知快照和高层动作意图之上接入规则化 `PolicyEngine` 与未来 `LlmPolicyEngine`。
2. 让 `LLM` 只负责任务选择、链路切换、异常恢复和策略建议。
3. 保持底层输入、熔断和安全守护仍由本地控制层负责。
4. 在无 LLM 模式下保留规则策略作为默认回退方案。
