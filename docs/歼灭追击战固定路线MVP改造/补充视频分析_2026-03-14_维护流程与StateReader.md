# 补充视频分析：维护流程与 StateReader

- 分析日期：2026-03-14
- 输入素材：
  - `/mnt/e/code/AradVision/assets/video/jmzjz_inventory_heathpotion.mp4`
  - `/mnt/e/code/AradVision/assets/video/jmzjz_shop_repair.mp4`
  - `/mnt/e/code/AradVision/assets/video/jmzjz_potion_cooldown.mp4`
- 视频规格：
  - `jmzjz_inventory_heathpotion.mp4`：`960x720`，`60 FPS`，约 `60.40` 秒
  - `jmzjz_shop_repair.mp4`：`960x720`，`60 FPS`，约 `13.97` 秒
  - `jmzjz_potion_cooldown.mp4`：`960x720`，`60 FPS`，约 `23.28` 秒
- 目标：确认维护流程真实约束，并为 `StateReader` 提供第一版可复验候选 ROI

## 1. 本轮新增事实

用户补充的关键约束如下：

1. 刷图结束后，回城镇阶段存在时间限制，超时会自动回城。
2. 在这一短窗口里卖货并不稳定，容易被中断。
3. 因此，`jmzjz_shop_repair.mp4` 不是“结算后立刻卖货”的样本，而是“从副本等待处走到最近商人并打开维修界面”的样本。

这意味着：

1. P0 维护流程不能假设“`run_finished` 出现后立刻卖货”。
2. 当前更合理的维护基线应是“回到稳定城镇等待区后，走最近商人并打开维修界面”。
3. `MaintenanceController` 当前只能表达状态切换，尚不能把“结算态”和“稳定城镇维护态”区分开。

## 2. 两段补充视频分别解决了什么问题

### 2.1 `jmzjz_inventory_heathpotion.mp4`

这段视频可以支持确认：

1. 右侧背包窗口打开后，真实重量条确实可见。
2. 底部左侧药水栏中，`1`、`2` 键位与用户口述一致。
3. 药水数量在样本中有变化，说明“药水库存”存在真实视觉信号。

这段视频当前还不能支持确认：

1. `free_slots` 的可靠读取规则。
2. 仅凭战斗 HUD 直接读取重量条。

结论：

`inventory_weight_ratio` 的真实读取应建立在“背包窗口已打开”的前提下，不能继续把战斗 HUD 某个固定区域当成重量条。

### 2.2 `jmzjz_shop_repair.mp4`

这段视频可以支持确认：

1. 左侧商店窗口和底部蓝色按钮条在打开后稳定存在。
2. 右侧背包窗口、重量条和整理按钮同时可见。
3. “走最近商人 -> 打开维修界面”这条维护入口路线是可复现的。

这段视频当前还不能支持确认：

1. 真实出售点击路径。
2. 从结算态直接无缝衔接到商人界面的时序细节。
3. 卖货完成后的关闭窗口或回刷图入口逻辑。

结论：

`vendor_ui_open` 应绑定到左侧商店窗口或底部按钮条，而不是继续绑定当前错误的右侧人物/装备区。

### 2.3 `jmzjz_potion_cooldown.mp4`

这段视频补齐了此前缺失的冷却负样本。

当前可以确认：

1. 左下药水栏里存在“可用态 -> 冷却态 -> 恢复可用”的稳定切换。
2. 在本次样本中，最稳定的变化落在中间药水槽位。
3. `00:12 - 00:20` 左右可以作为冷却态样本区间，`00:00 - 00:10` 与 `00:22` 左右可作为可用态样本区间。

这段视频当前仍不能支持确认：

1. 药水耗尽后的空槽或 `0` 库存样本。
2. 多种药水类型混用时是否仍然共享同一套冷却视觉信号。

结论：

`potion_cd_ready` 可以开始用单槽位 ROI 做第一版实机读取，但 `potion_stock_available` 仍然没有“空库存”反例。

## 4. 对当前配置的直接修正意见

### 4.1 `inventory_weight_bar`

当前 `configs/config.yaml` 中：

```yaml
inventory_weight_bar: [812, 618, 110, 20]
```

这块区域实际上偏到了右下角圆盘附近，不是背包里的真实重量条。

基于补充视频，第一版候选值更接近：

```yaml
inventory_weight_bar: [523, 546, 160, 20]
```

但这里有一个前提：

只有在背包窗口可见时，这个 ROI 才有真实语义。

### 4.2 `inventory_flag`

当前仓库之前没有单独的背包窗口前置判断 ROI。

基于补充视频，第一版候选值为：

```yaml
inventory_flag: [540, 58, 250, 24]
```

它的作用不是读取具体数值，而是先判断“背包窗口是否真的已经打开”，避免把战斗 HUD 误读成重量条。

### 4.3 `vendor_flag`

当前 `vendor_flag`：

```yaml
vendor_flag: [650, 150, 170, 70]
```

这块区域主要落在右侧人物/装备区，不足以表示“商店已打开”。

下一轮更合理的做法有两种：

1. 以左侧商店标题条为主信号。
2. 以底部蓝色按钮条为主信号。

如果只保留一个配置项，优先建议先试：

```yaml
vendor_flag: [84, 606, 372, 46]
```

### 4.4 `potion_flag`

当前 `potion_flag`：

```yaml
potion_flag: [118, 606, 120, 44]
```

基于 `jmzjz_potion_cooldown.mp4`，更适合当前实现的第一版候选值为：

```yaml
potion_flag: [130, 632, 48, 42]
```

更稳妥的当前结论是：

1. `potion_cd_ready` 已经有第一版可复验 ROI。
2. `potion_stock_available` 仍然没有空槽负样本，暂时只能保守实现。

## 5. 对代码边界的直接影响

### 5.1 `StateReader`

当前实现的问题不是只差阈值，而是缺少 UI 前置状态：

1. `inventory_weight_ratio` 需要“背包已打开”的前置判断。
2. `vendor_ui_open` 需要“商店窗口已打开”的前置判断。
3. `free_slots` 若要做实，必须单独建立格子网格规则，不能继续返回占位值。
4. `potion_cd_ready` 已补齐冷却负样本，但 `potion_stock_available` 仍缺空库存反例。

### 5.2 `MaintenanceController`

当前控制器：

1. 看到 `RUN_FINISHED` 就进入维护态。
2. 没有“已经回到稳定城镇等待区”的单独状态。
3. 没有“从等待区走最近商人”的建模。

因此当前更准确的描述应是：

仓库已经具备“进入维护分支”的主链路，但尚未具备“稳定城镇维护路线”的真实执行逻辑。

## 6. 当前能确认与不能确认的结论

### 6.1 当前能确认的

1. 维护流程实机样本应以“等待区 -> 最近商人 -> 维修界面”为基线。
2. 背包重量条不是战斗 HUD 固定元素，而是背包窗口内元素。
3. 商店打开信号在左侧商店窗口和底部按钮条上更稳定。
4. 药水 `1/2` 键位与用户环境一致，且冷却态已经有稳定视频样本。

### 6.2 当前还不能确认的

1. `free_slots` 的可靠规则。
2. `potion_stock_available` 的空库存负样本阈值。
3. 结算态到稳定城镇维护态的完整自动切换规则。
4. 真实卖货点击和维修点击的安全执行边界。

## 7. 下一步最合理的实现顺序

1. 先把这份文档中的候选 ROI 作为下一轮 `StateReader` 复核基线。
2. 先增加“背包窗口 / 商店窗口是否打开”的辅助判断，再谈重量和维护信号。
3. `free_slots` 与 `potion_stock_available` 继续保持谨慎，不用伪实现冒充完成。
4. 等维护路线被建成“等待区 -> 最近商人”后，再把 `MaintenanceController` 从纯状态切换推进到真实联调。
