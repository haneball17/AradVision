## 4. 我看完视频后，你第二批再提供的资料

这一批不要先做，等我先拆完完整流程再给。

### 4.1 关键时间点截图

至少覆盖以下场景：

1. 普通房战斗中
2. 清房瞬间
3. 过图黑屏或转场
4. Boss 房
5. 通关结算
6. 背包接近满重
7. 药水可用
8. 药水不可用或冷却中
9. 商店/维修相关界面出现

目的：

1. 复核 `MainViewReader`
2. 复核 `MinimapReader`
3. 复核 `StateReader`

补充约束：

如果副本结算后存在自动回城倒计时，且短窗口内卖货容易中断，那么商店/维修样本不要求从“结算后立刻卖货”开始录。
优先采用“回到稳定城镇等待区后，走最近商人并打开维修界面”的素材，这种素材更适合 P0 的维护流程建模。

### 4.2 误判样本

格式：

```text

```

目的：

让阈值、稳定帧数和房间脚本基于真实错例收口，而不是靠猜。

## 9. 外部资料补充结论

本轮已核实的公开资料能补的是“通用 DFO 语义”，不能替代你的《歼灭追击战》实机素材。

可直接参考：

1. DFO 官方 Fatigue Points 指南  
   <https://www.dfoneople.com/gameinfo/guide/Start-Leveling%21/Basic-Leveling/Fatigue-Points>
2. DFO 官方 Equipment Repair 说明  
   <https://www.dfoneople.com/news/updates/3368/Qol-Improvements/Equipment-Repair>
3. DFO 官方 Urgent Repair Function 说明  
   <https://www.dfoneople.com/news/updates/221/System-Upgrade/Miscellaneous-System/Urgent-Repair-Function>
4. StrategyWiki 的 DFO Gameplay 页面  
   <https://strategywiki.org/wiki/Dungeon_Fighter_Online/Gameplay>

这些资料能帮助我们确认：

1. 疲劳值按房间消耗，不适合作为房间识别主信号，但能辅助理解完整流程长度
2. 维修/紧急维修确实是游戏内稳定存在的系统语义，后续维护流程可以围绕明确的 UI/触发点设计
3. 通关后出现 NPC 维修/购物相关交互是合理研究方向，但具体到《歼灭追击战》的维护入口，仍需以你的实机视频为准

GitHub 侧这轮没有找到能直接复用、且足以作为《歼灭追击战》路线事实来源的稳定仓库，因此实现边界仍以本仓库当前 `Reader + Controller` 结构为准。
