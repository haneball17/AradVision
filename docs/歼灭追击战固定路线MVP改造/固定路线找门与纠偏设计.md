# 固定路线找门与纠偏设计

- 日期：2026-03-15
- 适用范围：《歼灭追击战》固定路线 MVP 的副本内推进设计
- 文档定位：实现前设计稿，只定义后续实现边界，不代表当前代码已经全部具备下述能力
- 事实来源：当前本地代码与配置、既有实机分析文档、联网核实的公开资料

## 1. 背景与问题定义

围绕《歼灭追击战》固定路线 MVP，当前“找下个门”面临的真实问题主要有：

1. 房间很大，门往往不在初始视野中，不能假设清房后立刻能在屏幕里看到门。
2. 一个房间可能存在多个出口，不能把“先看到哪个门”误当成“就该进哪个门”。
3. 角色在移动过程中会受击退、击飞、眩晕、减速、输入延迟和平台落差影响，单次长按脚本很容易失真。
4. 当前主线仍是固定路线 MVP，不适合直接升级成整图通用寻路或环境建模。

因此，本设计不把问题定义成“通用 pathfinding”，而是定义成：

**固定路线下的定向出门与局部纠偏**

## 2. 当前已实现事实与后续设计边界

### 2.1 当前已实现事实

- 当前 `RouteRunController` 已经根据 `room_scripts.expected_exit_direction`、`exit_action_template` 与 `MinimapPathState` 触发房间推进。
- 当前 `MinimapReader` 负责输出 `NEIGHBOR_FLASH_QMARK`、`BOSS_ONLY_READY` 等推进校验信号，而不是像素级导航路径。
- 当前配置里已经有 `door_confirmation_roi` 和 `transition_timeout_ms` 结构预留。

### 2.2 本文定义的后续设计边界

- “去哪边”由固定路线 `room_scripts` 决定，不由 YOLO 临场决定。
- YOLO 负责动态空间目标辅助感知，优先用于 `hero` 位置和局部门候选检测。
- 门确认只在目标方向局部窗口内进行，不做整屏搜门来决定路线。
- 脚本失败后先进入房间级纠偏和局部恢复，再考虑更通用的恢复逻辑。
- 小地图主要用于路线校验、房间索引确认、过图确认和异常恢复，不作为精确导航器。

## 3. 总体方案

整体流程采用三阶段：

1. `SEEK_EDGE`
   - 去目标边缘工作区。
   - 目标不是立刻进门，而是先把角色带到“门大概率会进入视野”的区域。
2. `SCAN_DOOR`
   - 在目标边缘工作区局部扫描门。
   - 只在目标方向局部窗口内识别 `gate`，不做整屏门搜索。
3. `ALIGN_AND_ENTER`
   - 已有稳定门候选后，使用短步对准并进入门判定区。

成功主判据保持不变：

- `main_view_state == TRANSITION`
- 小地图状态推进
- 房间索引推进

只要任一成立，就视为过图成功，不要求“看见门”成为唯一成功条件。

## 4. 参与数据与信号

### 4.1 必要信号

| 信号 | 用途 |
| --- | --- |
| `expected_exit_direction` | 决定当前房间目标出口方向 |
| `room_feature_tag` | 决定该房间的边缘工作区和纠偏模板 |
| `main_view_state` | 判断战斗、清房、过图、Boss、通关 |
| `minimap_path_state` | 判断房间推进是否合理、是否可进入下一房 |
| `door_confirmation_roi` | 做局部门前确认，不做全图搜门 |
| `transition_timeout_ms` | 控制单房间出门等待与恢复节奏 |

### 4.2 建议新增的感知信号

| 信号 | 建议职责 |
| --- | --- |
| YOLO `hero` | 提供稳定人物检测框，推导 `foot_point` |
| YOLO `gate` | 提供目标方向局部门候选 |
| `hero` 位置历史 | 做卡住判定、阶段切换、纠偏决策 |
| 阶段重试计数 | 控制分层恢复，避免无限乱跑 |

### 4.3 人物位置口径

- 人物站位建议主用 YOLO `hero`。
- 运行期建议使用 `hero bbox` 的底边中点作为 `foot_point`。
- 不建议用纯 ROI 去判断人物位置，因为人物姿态会随着走路、跑步、滑铲、跳跃和受击变化。

## 5. 三阶段状态机

### 5.1 `SEEK_EDGE`：去目标边缘工作区

目标：

- 把角色带到目标方向的边缘工作区，而不是立刻进门。

执行规则：

- 使用短步移动，不发超长 MOVE。
- 单步移动后立即检查是否有真实进展。
- 只朝 `expected_exit_direction` 指示的方向推进。

阶段结束条件：

- 满足边缘工作区阈值。
- 或门已提前进入目标方向扫描窗口。
- 或已经进入 `TRANSITION`。

### 5.2 `SCAN_DOOR`：边缘扫描找门

目标：

- 在目标边缘工作区局部找到门，而不是在整张图上猜测门。

执行规则：

- 只在目标方向局部窗口内启用门检测。
- 允许执行 2 到 3 套扫描模板，例如“右移小步 -> 停 -> 跳 -> 再右移”。
- 扫描期间持续复核小地图和主画面状态。

阶段结束条件：

- 目标方向门候选连续多帧稳定出现。
- 或已经进入 `TRANSITION`。

### 5.3 `ALIGN_AND_ENTER`：对准并进门

目标：

- 在已有稳定门候选的前提下，通过短步微调进入门判定区。

执行规则：

- 若门在角色右侧，则短步右移；在左侧则短步左移。
- 若门相对角色明显偏上，则先做上移或跳跃；明显偏下则先做下落或下移。
- 不追求像素级中心对齐，只要求进入门判定区。

阶段结束条件：

- `TRANSITION`
- 小地图推进
- 房间索引推进

## 6. 边缘工作区判定规则表

这里的阈值不是“角色是否碰到地图最边缘”，而是“角色是否进入了扫门工作区”。

| 方向 | 首版判定公式 | 说明 |
| --- | --- | --- |
| `RIGHT` | `hero_x_ratio >= edge_trigger_x` | `edge_trigger_x` 建议先按房型给默认值，右门普通房可从 `0.68 ~ 0.72` 起步 |
| `LEFT` | `hero_x_ratio <= edge_trigger_x` | 左门普通房可从 `0.28 ~ 0.32` 起步 |
| `UP` | `hero_y_ratio <= edge_trigger_y` 且 `platform_x_min <= hero_x_ratio <= platform_x_max` | 上门房不能只看 `y`，否则角色可能只是跳起来了，不一定到了正确平台 |
| `DOWN` | `hero_y_ratio >= edge_trigger_y` 且 `lower_x_min <= hero_x_ratio <= lower_x_max` | 下门房同样需要结合横向工作区，不宜只看 `y` |

补充规则：

- 如果门已经稳定进入目标方向扫描窗口，可以提前跳过边缘阈值，直接进入 `SCAN_DOOR`。
- `UP` / `DOWN` 房建议按房间单独定值，不建议先做跨房间统一阈值。

## 7. 多门房的局部筛选算法

多门房的核心原则是：

**先由路线决定方向，再在目标方向局部窗口里挑门。**

具体步骤：

1. 从 `room_idx` 读取当前房间的 `expected_exit_direction`。
2. 按方向裁剪候选窗口：
   - `RIGHT`：只保留屏幕右侧工作区内的 `gate`
   - `LEFT`：只保留屏幕左侧工作区内的 `gate`
   - `UP`：只保留目标平台区域内的 `gate`
   - `DOWN`：只保留下落区或下沿工作区内的 `gate`
3. 如果目标窗口内有多个候选门，按以下优先级排序：
   - 连续帧稳定性更高
   - 更接近目标边缘
   - 与当前平台高度更匹配
   - 检测框面积更大、置信度更稳定

不采用的策略：

- 不用“全屏最近门优先”。
- 不用“先看到哪个门就进哪个门”。
- 不让 YOLO 单独决定“这房该走哪条路”。

## 8. 卡住判定与分层纠偏

### 8.1 卡住判定

当前 MVP 建议主用 `hero` 位置历史做卡住判定：

1. 连续若干帧都在发送 MOVE。
2. `hero.foot_point` 朝目标方向的位移增量持续低于最小阈值。
3. 同时没有门确认、没有过图、没有小地图推进。

这三者同时成立时，判定为“无进展”或“卡住”。

不建议作为主判据的信号：

- 背景变化
- 光流变化
- 障碍物 YOLO 检测

这些信号首版可以作为观察面，但不应成为 MVP 主判据。

### 8.2 分层纠偏梯子

建议把失败恢复做成固定梯子：

1. 原始出门模板
2. 小步重试
3. 定向跳跃/位移纠偏
4. 目标边缘局部搜索
5. 回安全点后二次出门
6. 最后才记异常

设计目的：

- 不因为一次受击、一次延迟、一次平台卡位就直接停机。
- 又避免无限乱跑、无限重试。

## 9. 脚本失败后的升级策略

主用基线仍应是副本内置脚本：

1. 先按 `room_scripts` 尝试房间级出门。
2. 若超时未过图，先进入房间级纠偏和局部恢复。
3. 若房间级策略仍失败，再进入“局部通用恢复”。

这里的“局部通用恢复”含义是：

- 仍然局限在当前房间和当前目标方向内工作；
- 允许利用 `hero + gate` 的相对位置做短步修正；
- 不等同于首版就上完整的全图通用寻路或 A*。

## 10. 小地图房间模板与拓扑状态

当前建议维护的是“房间级小地图模板/拓扑状态”，而不是完整几何建图。

建议用途：

- 校验当前房间索引是否合理
- 校验当前房间的预期出口方向是否合理
- 判断是否已经进入 Boss 前房或特殊房
- 在脚本失真时辅助恢复路线

建议形式：

- 房间级门向模板
- 房间级相邻房状态模板
- `expected_room_index -> minimap expectation` 的映射

不建议当前阶段做的事情：

- 完整 SLAM
- 依赖小地图做像素级移动控制
- 用小地图替代 `room_scripts`

## 11. 阈值失效时的自动修正口径

阈值失效后不应立即报错停机，也不应在运行中直接永久改配置。

建议口径：

1. 若门比阈值更早进入视野：
   - 记录“当前阈值偏晚”的观察结论；
   - 后续实机复核时把阈值向更早方向微调。
2. 若达到阈值后长时间仍无门：
   - 先做局部扫描和纠偏；
   - 仍无门时记录“当前阈值偏早”或“房间脚本动作不足”的观察结论。
3. 若经常到不了目标工作区：
   - 优先检查 `exit_action_template` 和纠偏模板，而不是先改阈值。

## 12. 当前已实现事实与规划边界总结

当前已实现事实：

- 固定路线方向由 `room_scripts` 决定。
- 小地图与主画面承担推进校验职责。
- 房间推进已具备首版模板和过图超时控制。

本文定义的规划边界：

- `hero` 位置建议主用 YOLO。
- 出门应升级为“三阶段 + 分层纠偏”状态机。
- 多门筛选只在目标方向局部窗口内进行。
- 脚本失败后先局部恢复，再视情况补更通用的恢复能力。
- 小地图模板用于校验与恢复，不用于精确导航。
