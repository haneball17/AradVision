# 固定路线 YOLO 辅助感知与清房拾取设计

- 日期：2026-03-16
- 适用范围：《歼灭追击战》固定路线 MVP 的局部 YOLO 训练与运行期接入设计
- 文档定位：实现前设计稿，只定义后续实现边界，不代表当前代码已经全部具备下述能力
- 事实来源：当前本地代码与配置、现有主线文档、联网核实的 Ultralytics 官方资料

## 1. 背景与目标

当前主线仍是《歼灭追击战》固定路线 MVP，不是“通用 YOLO 主链路”。因此，YOLO 的目标不是替代固定路线控制器，而是补足当前 Reader 与固定脚本在动态空间目标上的短板。

本设计要解决两类问题：

1. 副本内找门与局部恢复缺少稳定的人物位置和局部门候选反馈。
2. 物品掉落在角色脚边，但当前没有“清房后局部拾取”的稳定闭环。

因此，当前 YOLO 训练和接入的唯一主线应定义为：

**固定路线下的局部辅助感知**

## 2. 当前已实现事实与后续边界

### 2.1 当前已实现事实

- `FixedRoutePipeline` 会把检测结果中的 `hero / items / doors` 分类后写入 `GameContext`。
- 当前默认检测器仍以 `MockYoloDetector` 为主，真实 YOLO 检测器尚未成为现行主链路。
- 当前 `RouteRunController` 还没有“清房后脚底拾取阶段”，清房后默认直接进入出门流程。
- 仓库里已有原始数据采集和分布分析脚本：
  - `scripts/capture_training_data.py`
  - `scripts/analyze_dataset.py`

### 2.2 本文定义的后续边界

- 固定路线脚本继续负责“该去哪边”。
- YOLO 负责“画面里的动态空间目标在哪里”。
- `hero` 用于人物站位、卡住判定、边缘工作区判断。
- `gate` 用于目标方向局部门确认，不参与路线方向决策。
- `item` 只用于清房后脚底局部拾取判断，不扩展成战斗中整屏拾取系统。

## 3. 统一职责划分

| 能力 | 主负责模块 | 当前口径 |
| --- | --- | --- |
| 下一扇门方向选择 | `room_scripts.expected_exit_direction` | 固定路线决定 |
| 角色位置与位移反馈 | YOLO `hero` | 局部动态感知 |
| 目标方向门是否进屏 | YOLO `gate` | 只在目标方向局部窗口确认 |
| 清房后脚底是否有掉落 | YOLO `item` | 只在脚底局部窗口确认 |
| 过图是否成功 | `MainViewReader` / `MinimapReader` | 仍由状态读数主判定 |

不采用的职责划分：

- 不让 YOLO 决定“这房该往哪边走”。
- 不做整屏 `item` 检测主链路。
- 不做战斗中通用掉落导航。

## 4. 训练顺序

### 4.1 阶段 A：`hero`

目标：

- 提供稳定的 `hero bbox`
- 从 `bbox` 推导 `foot_point`
- 服务边缘工作区判定、卡住判定、恢复反馈

数据重点：

- 走路、奔跑、滑铲、受击、跳跃
- 平地房、平台房、门前、边缘区
- 被击退、被障碍卡住、恢复探测

建议起步量：

- 400 到 600 张可启动
- 1000 张左右形成首个稳定版

### 4.2 阶段 B：`hero + gate`

目标：

- 服务固定路线下的三阶段找门：
  - `SEEK_EDGE`
  - `SCAN_DOOR`
  - `ALIGN_AND_ENTER`

数据重点：

- 门刚进屏
- 多门房
- 大房间边缘
- 平台门 / 下落门
- 特效干扰和复杂背景

建议有效样本：

- `gate` 目标 500 到 800 张

### 4.3 阶段 C：`hero + gate + item`

目标：

- 服务清房后脚底局部拾取闭环

数据重点：

- 清房后脚边单个掉落
- 清房后脚边多个掉落
- 技能特效遮挡
- 脚底复杂背景但无掉落
- 门前掉落与普通地板混合

这里的 `item` 不是为了整屏识别，而是为了“清房后脚底局部确认”。

## 5. 数据采集与标注

### 5.1 采集原则

- 只采《歼灭追击战》
- 固定当前主线分辨率：`960x720`
- 固定窗口模式、DPI 和 HUD 形态
- 只保留与当前主线直接相关的样本

原始素材采集继续复用：

- `scripts/capture_training_data.py`

数据分布检查继续复用：

- `scripts/analyze_dataset.py`

注意：

- 这两个脚本当前只适合 raw 素材采集和分布检查，不代表正式训练集已经在仓库内成型。
- 当前 `scripts/label_guide.py` 仍有历史语法问题，不应作为当前训练主工具依赖。

### 5.2 标注规则

`hero`

- 框角色主体
- 不按姿态拆分子类
- 遮挡时尽量保留主体框

`gate`

- 框可进入的门结构
- 非目标方向门也可标，用于训练泛化
- 运行时仍由脚本先定方向再裁剪候选

`item`

- 只框真实可拾取掉落物
- 首版不细分物品类型
- 必须补大量脚底无掉落的负样本

### 5.3 训练集目录建议

```text
datasets/dnf_jmzjz_yolo_v1/
  images/
    train/
    val/
    test/
  labels/
    train/
    val/
    test/
  data.yaml
```

推荐切分：

- train: 70%
- val: 20%
- test: 10%

切分原则：

- 按视频段切分，不把连续近邻帧同时放进 train 和 val

## 6. 训练参数建议

首版建议直接使用 Ultralytics detect 训练流程：

```bash
yolo detect train \
  model=yolov8n.pt \
  data=datasets/dnf_jmzjz_yolo_v1/data.yaml \
  imgsz=640 \
  epochs=100 \
  batch=16 \
  device=0 \
  project=runs/detect \
  name=jmzjz_assist_v1
```

建议默认值：

- 模型：`yolov8n.pt`
- `imgsz=640`
- `epochs=80 ~ 120`
- `batch=16` 起试
- `patience=20`
- `pretrained=True`

官方参考：

- <https://docs.ultralytics.com/>
- <https://docs.ultralytics.com/datasets/detect/>

## 7. 运行期接入方案

### 7.1 找门链路

运行期职责保持如下：

1. `room_scripts.expected_exit_direction` 决定当前房间目标方向。
2. `hero` 用于判断角色是否进入目标边缘工作区。
3. 进入目标边缘工作区后，只在该方向局部窗口启用 `gate`。
4. `gate` 负责门进屏确认和门前短步对准辅助。
5. 过图成功仍以 `TRANSITION`、小地图推进和房间索引推进为主判据。

### 7.2 清房后拾取链路

清房后的推荐顺序：

1. 清房确认
2. 若存在 `hero`，裁剪人物脚底局部窗口
3. 仅统计脚底局部窗口内的 `item`
4. 若无 `item`，直接进入出门流程
5. 若有 `item`，按一次 `pick_up`，即 `X`
6. 每次按键后复检
7. 达到预算或无 `item` 后退出拾取阶段

默认策略：

- `max_pickup_presses_per_room = 4`
- 每次按键后都要复检
- 达到预算后不再死循环，继续主线推进

这个阶段的目标是“尽量捡脚边掉落”，而不是“保证整房间全捡”。

## 8. 验收口径

`hero`

- 大部分帧稳定检出
- `foot_point` 可用于位移和卡住判定

`gate`

- 在目标边缘工作区内稳定进屏
- 不明显误导多门房筛选

`item`

- 清房后脚底有掉落时能触发拾取
- 脚底无掉落时不会长时间空按
- 预算上限能防止误检导致死循环

模型指标建议按项目用途收口：

- `hero`：`mAP50 >= 0.75`
- `gate`：`mAP50 >= 0.65`
- `item`：更重视脚底局部场景的低误检和复检稳定性，而不是追求整屏高 mAP

## 9. 当前边界总结

当前已明确：

- YOLO 当前是固定路线 MVP 的辅助层，不是主决策层。
- `item` 只为清房后脚底局部拾取服务，不进入战斗中主检测链路。
- 训练应分阶段推进，先做 `hero`，再加 `gate`，最后再评估是否并入 `item`。
- 若 `item` 误检成本过高，可以退化成“清房后固定补按 `X` 若干次”的无检测方案。
